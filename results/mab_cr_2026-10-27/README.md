# MAB-CR 四方法对照实验（2026-10-27）

**任务**：MemoryAgentBench Conflict Resolution —— 同一事实键在上下文里被反复改写，
答案永远取**最新**的值。这是主线问题③（动态更新）在真实公开数据上的第一组测量。

## 1. 协议

| 项 | 设置 |
|---|---|
| 数据 | `Conflict_Resolution-*.parquet` 官方原题，每问可见事实 `cap=32`（金标链 + **同键全部冲突版本** + BM25 相关事实），train 500 / val 300 按 context 源切 |
| 记忆单元 | 一条事实一个槽位；`unit_meta[i] = {fact, entity, relation, time=事实编号, distractor}` |
| 时间轴 | 事实编号（MAB 无时间戳，编号越大越新） |
| 判定 | 归一化整串相等；答案字段官方 `answers` 双层 list，取命中任一 |
| 方法 | 与 HotpotQA 完全同一条 `eval_latent_table.py` 路径，同一冻结模型 |

## 3. 这组数字说明什么（如实报告）

1. **FST 的组级寻址学到了东西，版本级没有**：group 0.650 > 0.550（恒选第一组），
   `read_acc 0.65 > 0.05`（普通 Router 只有 5%）——事实键编码器 + 两级结构在真实数据上
   确实把"该读哪条事实"做出来了。但 ver 0.525 **低于"恒选最新版"的 0.885**：
   版本选择学到的东西不如一个"总是取最新"的规则。这与 CR 的结构一致——
   88.5% 的多版本问题里最新版就是答案，版本级监督（CE over versions）在 300 题内
   没学过这个先验。
2. **acc 2.5% 是结构性上不去**：CR 的题多为两跳链（"spouse of the author of X 的国籍"），
   每问需要 ≥2 条事实，而两种潜层方法每次只读 **1 个槽（4 软 token）**。
   `oracle` 给 1 条金标事实也只有 32%（单跳事实对两跳题本就不够）。
   所以这列是"单槽读出 vs 两跳任务"的不对等比较，报告里必须写明。
3. **明文基线也不高（17.0%）**：top-4 检索命中率 95% 但准确率 17%，top-32 反而降到 14%
   （更多干扰事实），说明 CR 上"读出"同样受两跳限制，不只是检索问题。
4. **开销差距大**：FST 每问 11.0s（32 个槽位逐条编码 + 两级寻址）vs Router 2.2s vs
   text-top4 1.5s。FST 的编码成本随槽数线性增长，这是设计代价，须与"读对槽位 65%"放在一起看。

## 4. 下一步（按主线问题③的要求）

1. FST 支持两跳链式读出（`generate_latent_answer_fst` 目前硬编码 hops=1），
   否则 CR 这列永远是不对等比较。
2. hist-max 扫描（4 → 1/2/8）：验证"历史容量"与"当前值准确率"的权衡，
   这是 FST-Mem 相对 StatePool 的核心卖点。
3. LME knowledge-update（78 题）接入：那是带真实时间戳的更新任务，能同时给出
   更新准确率与历史访问准确率两列。
