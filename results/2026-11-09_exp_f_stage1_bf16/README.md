# 2026-11-09 实验 F 阶段一：2 KiB/token 的存储精度复核

**这一轮只回答一个问题**：实验 F 阶段一的成绩是不是靠 fp32 中间量撑起来的？

结论：**不是。存储用 fp16/bf16（2 KiB/token）与 fp32（4 KiB）完全等价，41.0% 一分不掉。**
但**训练时**若一直按量化后的潜码回传梯度，模型会落到明显更差的解（41.0 → 29.0）。

## 主表（同一权重，只改存储精度，n=200）

| 方法 | 存储 KiB/token | EM% | F1% | 相对原生 |
|---|---|---|---|---|
| `native`（原生 L6~35 KV） | 120 | 45.5 | 65.3 | 100% |
| `pca1024`（同前缀重拟合） | 2.0 | 20.5 | 33.9 | 45% |
| **`fadkv1_bf16`** | **2.0** | **41.0** | 59.5 | **90%** |
| **`fadkv1_fp16`** | **2.0** | **41.0** | 59.8 | **90%** |
| `fadkv1_fp32` | 4.0 | 41.0 | 59.5 | 90% |

三档逐题配对完全相同（28:37，p=0.3211），题型分层也逐项一致
（实体 33.1 / 日期 72.7 / 数字 71.4 / 是/否 87.5）。

配对（vs `native`）：`fadkv1` 差 −4.5（p=0.3211，已分不出差别）；
`pca1024` 差 −25.0（2:52，p<0.0001）。

## 关键区分：量化发生在训练时还是存储时

| 训练 | 存储 | EM% | 文件 |
|---|---|---|---|
| fp32，750 步 | fp16 / bf16 / fp32 | **41.0** | `eval.log`（本目录主表） |
| fp32，1000 步 | fp32 | 34.5 | （上一轮，已并入 RESULTS.md） |
| bf16，750 步（`L_attn` 有梯度） | 同 | 29.0 | `ablation_train_time_quant.log` |
| fp16，1000 步（关 `L_attn`） | 同 | 29.0 | `ablation_no_attn_fp16.log` |

**凡训练时就量化的都落在 29.0，与 `L_attn` 开不开无关。** 所以：
- 只做存储量化 → 免费
- 训练中也量化 → 每步都在给潜码加噪声，优化落到更差的解

这条修正了两个此前的错误归因：① 早先以为 41.0% 是靠 fp32 中间量（错，存储可压）；
② 中途以为 41→29 是 `L_attn` 造成的（错，关掉仍是 29.0）。

## 采信限定

- 主干为冻结纯 Qwen3-4B-Instruct-2507（无 adapter），bf16，生成不走 KV cache
- 750 步优于 1000 步（41.0 vs 34.5）；700/800 附近**未扫**
- `number` n=7、`date` n=11 不可单独引用；实体 166 题是主线
- 训练侧必须保持 fp32 潜码；`--latent-dtype` 只应作用于**存储与评测**
- 阶段二（锚点 30% + 背景 4:1 池化，约 1.03 KiB/token）仍未跑
