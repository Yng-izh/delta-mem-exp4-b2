## P0-2 Oracle 读出分解（200 题）

`eval_latent_table.py --mode ...` · 日志 `logs/2026-11-04/diag_readout.log` ·
原始 `readout/*.json`

| 读法 | acc% | EM% | 注入 token | prompt token | 每题 ms |
|---|---|---|---|---|---|
| `oracle`（明文金标） | 53.0 | **54.0** | 92.5 | 127.9 | 535 |
| `oracle_embed`（原始词向量，预算已对齐） | 19.0 | 19.0 | 17.9 | 66.3 | 722 |
| `oracle_lex`（只用 z_lex，α=0） | 10.5 | 10.5 | 64.5 | 112.8 | 3083 |
| `oracle_sem`（只用 Bridge(z_sem)） | 10.5 | 10.5 | 64.5 | 112.8 | 3075 |
| `oracle_latent`（当前方法） | 12.5 | 12.5 | 64.5 | 112.8 | 2900 |

参照：无记忆（`none`，500 题）11.2。

- **关键 1**：把金标证据的**原始词向量**直接注入（不压缩），只有 19.0% —— 与明文
  的 54.0% 差 35 个点。所以"压缩器丢信息"不是唯一原因，**token 预算本身**就压住了上限。
- **关键 2**：`oracle_embed` 用 17.9 个 token 得 19.0%，而潜层用 64.5 个 token 只有
  12.5%。**给得多反而更差**。
- 两条单腿（`z_lex` / `z_sem`）都 10.5%，低于无记忆，合起来 12.5%。
- 口径说明：`oracle_embed` 首轮按裸原文算块数（15.6 token）得 14.5%，按压缩器实际
  文本（`[标题] 原文`）对齐后（17.9 token）得 19.0%。**上表是后者**。

## P1-3 符号保真（50 条答错题）

`tools/diag_symbol_fidelity.py` · 日志
`logs/2026-11-04/diag_symbol_fidelity_round2.log` · 原始 `diag_symbol_fidelity.json`

- 50 条答错题（扫 59 条），其中**含答案**的金标槽 58 个（多块槽 43 个）。
- 命中率（选中词里出现答案词）：**碎片口径 29.3%**，**整词口径 36.2%**。
- 整词扩展能多救 **6.9 个点**，但仍有 ~64% 的含答案槽连整词都没抓到。
- Bridge 状态：α 均值 0.264，残差/直通比 0.474（与 v5 的失控诊断一致）。
- 典型样本（碎片化）：金标句 `Mercedes-AMG is headquartered in Affalterbach...`，
  选中 `['[', 'Mer', 'cedes', '-']` —— 一个词被切成多块，每块只抓到一片。
- **读法**：每块 32 token 只准带 4 个，随机命中率约 17%，实测 29.3% 只比随机好一点。
  所以瓶颈是"**带得太少 + 没有直接监督教它带哪个**"，不只是"带碎了"。
