# 实验 A：读出接口的能力上限（200 题，`probe_base_1000.pt`）

一句话：**接口没问题，压缩有问题。** 同样的 token 预算下，原生词 25.0% 而潜层 17.5%
（配对 McNemar p=0.044）；连"每槽只给 4 个词、每题 9.8 个 token"的 22.0% 都高于潜层
的 18 个向量。所以瓶颈不在"冻结模型读不了软 token"，而在**压出来的东西不如原样的词**。

## 设置

| 项 | 值 |
|---|---|
| 权重 | `probe_base_1000.pt`（1000 步，`--cov-weight 0`，无 L_cov） |
| 数据 | `hotpot_val500` 前 200 题，金标槽位直送（寻址假定全对） |
| 注入 | `user` 消息体内 `Evidence:` 段，`\n[j] ` 围栏，与训练同源 |
| 预算对齐 | 原生各臂与 `latent` **逐槽位**内容 token 数相同（工具硬核对，差 0.00） |
| 判定 | EM（归一化整串相等）+ 配对 McNemar |

## 主表

| 读法 | EM% | F1% | 每题内容 token | 每题 prompt |
|---|---|---|---|---|
| `none`（无记忆） | 9.5 | 19.5 | 0 | 48.3 |
| `text`（金标原文进 system） | 53.5 | 71.9 | 92.5 | 140.9 |
| **`latent`（当前方法）** | **17.5** | 28.2 | 17.9 | 83.5 |
| `raw_prefix`（句首截断） | 25.0 | 34.9 | 17.9 | 83.5 |
| `raw_salient`（token 级显著性） | 14.5 | 26.6 | 17.9 | 83.5 |
| `raw_word`（整词显著性） | **25.0** | 39.1 | 17.9 | 83.5 |
| `raw_full`（整句原生词，不压缩） | 56.0 | 73.5 | 104.4 | 170.0 |

配对（对 `latent`）：`raw_word` 14 比 28，**p=0.044**；`raw_prefix` 11 比 25，p=0.029；
`raw_full` 6 比 81，p<0.0001；`raw_salient` 18 比 11，p=0.26（不显著）。

## 预算扫描（原生整词，固定每槽预算）

| 每槽词数 | 每题内容 token | EM% | F1% | 与 latent 差 |
|---|---|---|---|---|
| 4 | 9.8 | **22.0** | 34.3 | +4.5pt |
| 8 | 19.6 | 27.0 | 38.6 | +9.5pt |
| 16 | 39.1 | 36.5 | 54.5 | +19.0pt |
| 24 | 57.4 | 46.0 | 65.2 | +28.5pt |
| 32 | 72.3 | 51.0 | 69.7 | +33.5pt |
| 48 | 90.9 | 54.0 | 71.4 | +36.5pt |

**追平点 ≤ 9.8 个 token**：扫描的最小档就已经超过潜层的 17.9 个向量，所以真实追平点
在扫描范围之外（更小的预算）。也就是说 **18 个潜向量的信息量 < 10 个原生词**。

## 按题型（EM%）

| 读法 | date (n=11) | entity (n=166) | number (n=7) | yesno (n=16) |
|---|---|---|---|---|
| `none` | 0.0 | 4.2 | 0.0 | 75.0 |
| `text` | 81.8 | 47.6 | 57.1 | 93.8 |
| `latent` | 9.1 | 13.3 | 0.0 | 75.0 |
| `raw_word` | 18.2 | 21.1 | 14.3 | 75.0 |
| `raw_full` | 81.8 | 50.0 | 71.4 | 93.8 |

yes-no 题四臂全是 75.0 = 无记忆基线，说明这批 yes/no 题**记忆根本没被用上**
（12/16 靠参数知识就答对）。date 与 number 是最能区分读出的两类。

## 三条读法互相印证

1. **接口是好的**：`raw_full`（104 token，走完全相同的注入代码，只是向量换成真实词）
   56.0%，与明文 `text` 53.5% 基本持平。所以"冻结模型读不了软 token"这个解释不成立。
2. **压缩在亏钱**：同预算 17.9 token，原生词 25.0% vs 潜层 17.5%；甚至 9.8 个原生词
   的 22.0% 也更高。
3. **短板是"选了哪些词"，不是"向量软不软"**：`oracle_lex`（只用 `z_lex`，本来就是
   真实词表向量，α=0）在同一权重上只有 17.5%（见 `RESULTS.md`），而 `raw_word`
   同样是真实词向量、同样 17.9 个位置，有 25.0%。**两者唯一的差别是挑词的依据**：
   压缩器的注意力选词比"按显著性挑词"差 7.5 个点。

## 口径与限制

- 单 seed、单个 1000 步探针权重（不是训练完整的正式模型）；200 题，EM 粒度 0.5%。
- 扫描的预算是**每槽**给的，每题实际 token 数随金标槽数变化（4 档 = 9.8 个 token）。
- `raw_word` 的挑词是启发式（大写/数字/长词/非停用词/问题里没出现过），且用了问题文本
  ——这是读出期允许的信号，但它不是"最优挑词"，所以 25.0% 是**下界**。
- `raw_prefix` 是傻截断（保留句首，通常是标题 + 实体名），它也能赢潜层，说明结论不依赖
  挑词启发式的好坏。
- 复现：`CKPT=$B/ckpt/probe_base_1000.pt SWEEP=4,8,16,24,32,48 LIMIT=200 bash runs/exp_a_capacity.sh`

# 第二轮：把压缩比从 8 倍降到 2 倍（`probe_mut8_1000.pt`）

动机：上表的诊断是"预算太小是主要损失"。验证办法是把 `--max-unit-tokens` 从 32
改成 8（同样 m=4 个向量只覆盖 8 个 token，压缩比 8x → 2x），重训 1000 步。
每题注入 token 从 17.9 涨到 **56.8**。

## 结果

| 读法 | 旧（18 token） | **新（57 token）** | 每题内容 token |
|---|---|---|---|
| `none` | 9.5 | 9.5 | 0 |
| `text` | 53.5 | 53.5 | 92.5 |
| **`latent`** | **17.5** | **30.5** | 56.8 |
| `raw_prefix` | 25.0 | 35.5 | 56.8 |
| `raw_salient` | 14.5 | 39.5 | 56.8 |
| `raw_word` | 25.0 | **43.0** | 56.8 |
| `raw_full` | 56.0 | 56.0 | 104.4 |

配对（对 `latent`）：`raw_word` 15 比 44，**p=0.0002**；`raw_salient` 15 比 35，
**p=0.0066**；`raw_prefix` 22 比 36，p=0.087；`raw_full` 11 比 65，p<0.0001。

预算扫描（原生整词，同一台机器、同一批 200 题）：4→22.0%、8→27.0%、16→36.5%、
24→46.0%、32→51.0%、48→54.0%、64→56.0%。
**追平点：每槽 16 个词（每题 39.1 token，36.5%）就超过潜层的 56.8 个向量。**

## 三条结论

1. **"预算太小"这条诊断成立**：压缩比降 4 倍，潜层 17.5% → **30.5%**（相对 +74%）。
2. **但压缩本身亏得更多了**：同预算下原生词 43.0% vs 潜层 30.5%，差距从 7.5 个点
   扩大到 **12.5 个点**，而且现在统计上很硬（p=0.0002）。换算成信息量：
   **56.8 个潜向量 ≈ 25~30 个原生词**（原生 19.6 token 是 27.0%，39.1 token 是 36.5%）。
3. **连"碎片级"和"傻截断"都超过了潜层**：`raw_salient`（token 级碎片）39.5%、
   `raw_prefix`（句首截断）35.5%，都高于 30.5%。所以在 57 个位置上，压缩器
   **没有把位置用好**——不是"位置不够"，是"放进去的东西不对"。

## 训练侧：编码学会了，读出没学会

| 指标 | `probe_base_1000`（32） | `probe_mut8_1000`（8） |
|---|---|---|
| 重建 tokF1 | 0.185 | **0.483** |
| 重建实体恢复 | 26.3% | **33.9%** |
| 重建数字恢复 | 10.0% | **36.7%** |
| 端到端 val full-match | 12.5 → 17.5 → 15.0% | **22.5 → 25.0 → 22.5%** |

压缩器**明显更能还原内容**（数字恢复 10% → 36.7%），但端到端验证集从第 0 步的
22.5% 到第 1000 步还是 22.5%——**训练没有把"编码保真"转换成"读出可用"**。
这是下一轮要查的东西：QA 损失的梯度有没有真的作用在"冻结模型能读的那部分"上。
